# Billing source review — October 29, 2026

Historical review of the previous implementation. Its findings were addressed by the later [lifetime Premium implementation](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/BILLING_IMPLEMENTATION_2026-10-29.md>), using client-only ownership confirmation as the owner requested. References to the removed legacy billing files below describe that earlier revision. The new implementation still requires owner-run compilation and Play license testing.

Verdict: partially implemented; not ready for release. This review is read-only with respect to app code. No build, installation, purchase, refund, or Play Console operation was performed.

## Active implementation

`PremiumScreen` constructs `Billing`, loads the price on entry, launches the purchase on its Unlock button, and ends the client connection when the screen is disposed. The active product ID is the non-translatable `lifetime` string resource, whose value is `lifetime`. The declared Billing Library version is 9.1.0.

`BillingManager` has no callers in the app. Its `premium_lifetime` product ID, purchase query and StateFlow do not participate in the running app's billing flow. Do not mistake that unused class's recovery code for functionality in the active implementation.

## Findings and fix checklist

1. **P1 — Premium does not remove the main banner.** [MainScreen.kt:250](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/Design/screens/MainScreen.kt:250>) checks Remote Config, preview visibility and authentication, but never Premium. `AdaptiveBannerAd` also does not check it. The only read of `getPremium()` outside storage is the startup interstitial check in [StartScreen.kt:106](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/Design/screens/StartScreen.kt:106>). A paying user can continue seeing banners despite the advertised No Ads benefit. Use a shared observable entitlement for every ad gate and destroy/remove an existing ad when Premium activates.

2. **P1 — Purchase recovery is unreachable.** [Billing.kt:590](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/Billing.kt:590>) defines `restorePurchases`, but nothing calls it and there is no Restore Purchases action. The active implementation queries owned purchases only inside this unused restore path. Reinstall, cleared app data, process death during checkout, and a pending purchase completed while the screen/client is absent therefore have no recovery path. Query purchases after connection and on foreground return, process them through the same purchase handler, and wire a manual restore action. Reconcile after `ITEM_ALREADY_OWNED` rather than reporting a generic failure.

3. **P1 — Failed acknowledgment has no recovery.** [Billing.kt:530](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/Billing.kt:530>) returns when disconnected and only logs a failed acknowledgment. There is no retry schedule or recovery via a subsequent automatic owned-purchase query. A temporary failure can consequently remain unacknowledged. Add bounded retries/backoff and a durable recovery path. Granting a verified PURCHASED entitlement before acknowledgment is not itself the bug; missing verification and reliable fulfillment/acknowledgment recovery are the gaps. Google requires acknowledgment within three days after completion, otherwise the purchase is automatically refunded and entitlement revoked. [Google's integration guidance](https://developer.android.com/google/play/billing/integrate), [retry guidance](https://developer.android.com/google/play/billing/errors).

4. **P1 — Revocation and durable fulfillment are not reconciled.** [Billing.kt:412](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/Billing.kt:412>) sets an in-memory flag and launches an independent IO coroutine to save `true`; persistence failure is only logged. Acknowledgment can proceed without waiting for that write. There is no active path that saves `false` when entitlement is revoked. A refunded/revoked purchase can leave the cached flag set; an acknowledged purchase followed by a failed local write/process interruption can leave a paying user without restored access. Make fulfillment idempotent and durable, synchronize ownership, and distinguish confirmed revocation from a temporary query/network failure. A plain refund and a refund with entitlement revocation are different; remove access when revocation is confirmed.

5. **Production security gap — No purchase verification is wired.** [Billing.kt:448](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/Billing.kt:448>) checks product ID and PURCHASED state, then grants Premium. No signature verification or server verification call appears in this project; tokens are used only for acknowledgment. Prefer verification on a secure backend, including expected product/package/token ownership and replay handling, before granting entitlement. Acknowledgment is not purchase verification. No backend deployment/configuration was available to inspect. [Google's purchase-security guidance](https://developer.android.com/google/play/billing/security).

6. **P2 — Price/offer state can mislead or fail.** [PremiumScreen.kt:74](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/Design/screens/PremiumScreen.kt:74>) displays `$6.99` before Play returns a price, and retains it if loading fails. Purchase remains enabled while loading, unavailable or already owned. [Billing.kt:376](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/Billing.kt:376>) does not select/pass an offer token. The singular offer accessor returns the backward-compatible option, so legacy configuration can work, but modern multiple-option/offer configuration is not explicitly supported. Select an eligible lifetime buy option, display its actual formatted price and pass its matching offer token. Handle unavailable products/offers explicitly. Actual Console configuration could not be verified. [Google's one-time offer guidance](https://developer.android.com/google/play/billing/one-time-product-multi-purchase-options-offers).

7. **P2 — Concurrent taps and lifecycle failures are not controlled.** [PremiumScreen.kt:558](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/Design/screens/PremiumScreen.kt:558>) has no purchase-in-progress guard. [Billing.kt:128](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/Billing.kt:128>) can call `startConnection` again while connection is already in progress, and [Billing.kt:395](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/Billing.kt:395>) only logs the immediate launch result. The client and Activity are owned by the paywall, so completion after navigation/recreation also depends on missing recovery. Queue/coalesce connection work, allow only one purchase request, check the Activity before launch, handle immediate errors, and keep entitlement processing independent of the paywall lifecycle. Repeated taps are a request/UX problem; this review does not claim that Play charges a non-consumable twice.

8. **P2 — Duplicate implementation and UI state are disconnected.** [BillingManager.kt:20](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/BillingManager.kt:20>) uses `premium_lifetime`, whereas the active implementation uses `lifetime`. `AppClass.isnotpro` has no readers and is not observable. The PRO screen does not observe purchase success or show an owned state. Consolidate the implementation around one product configuration and one observable entitlement; keep navigation as an explicit UI response to success rather than placing it inside billing code.

9. **P2 — Paywall footer actions are empty.** Terms and Privacy text have empty click callbacks in [PremiumScreen.kt:607](<D:/Afaq'sSpace/Test apps/ApplockN/MyApplication2/app/src/main/java/com/example/myapplication/Design/screens/PremiumScreen.kt:607>). Dummy destinations may remain as the owner previously requested, but the actions still need wiring. Billing messages are also hard-coded English strings rather than localized resources.

## Already present

- One-time `INAPP` product query and a fresh query before launching a purchase.
- Product-ID and PURCHASED-state checks in the active purchase handler.
- PENDING purchases do not grant Premium.
- Play-formatted localized price when loading succeeds.
- Pending one-time purchase support and automatic service reconnection enabled.
- Acknowledgment call, `isAcknowledged` check, and local DataStore persistence.
- Existing merged manifests contain `com.android.vending.BILLING`; it is supplied by the library, so the absence of an explicit main-manifest declaration is not a missing-permission bug.

These parts do not resolve the recovery, security and entitlement-enforcement findings above.

## Requirements and external verification still needed

- Confirm the actual Play Console product ID, active lifetime buy option, regional availability, price and package/signing setup. The active source uses `lifetime`; the unused manager's different ID does not prove the Console product is wrong.
- Agree whether Premium only removes ads or also restricts Vault capacity/Intruder features. Those features currently have no Premium entitlement checks. Do not introduce new paywalls without the owner's intended feature policy.
- After fixes, use license-test purchases for success, cancellation/decline, already-owned recovery, pending completion/cancellation with the app closed, acknowledgment failure/retry, reinstall/clear-data restore, confirmed refund/revocation, offline restart, rapid taps, rotation/navigation during checkout, and immediate ad removal. No payment flow was launched during this review. [Google's billing test guidance](https://developer.android.com/google/play/billing/test).
- No build or device test result is claimed by this source review.
